# Golden Example — Post Structure Blueprint

This is the structural pattern every post should follow. Analyzed from a high-performing post.

## Golden Example (actual post)

```
I stopped writing better prompts. I started writing better specs.

The biggest challenge with AI coding isn't generating code.

It's agreeing on what to build.

We introduced one simple rule on our production Java platform:

𝗕𝗲𝗳𝗼𝗿𝗲 𝗰𝗵𝗮𝗻𝗴𝗶𝗻𝗴 𝗰𝗼𝗱𝗲, 𝘄𝗿𝗶𝘁𝗲 𝗮 𝗼𝗻𝗲-𝗽𝗮𝗴𝗲 𝗽𝗿𝗼𝗽𝗼𝘀𝗮𝗹.

What's changing?
What's not changing?
What can we reuse?
Why this approach?

We used 𝗢𝗽𝗲𝗻𝗦𝗽𝗲𝗰 to make that part of our workflow.

After shipping 𝟱𝟰 𝗳𝗲𝗮𝘁𝘂𝗿𝗲𝘀, something changed.

PR reviews stopped debating 𝘸𝘩𝘢𝘵 we were building.

They focused on whether the implementation matched the spec.

Design discussions moved out of pull requests.

New engineers onboarded by reading decisions instead of digging through Slack and git history.

The surprising part?

Spending 𝟮𝟬 𝗺𝗶𝗻𝘂𝘁𝗲𝘀 𝘄𝗿𝗶𝘁𝗶𝗻𝗴 𝗮 𝘀𝗽𝗲𝗰 regularly saved hours of rework, review cycles, and misaligned implementations.

As AI becomes part of every development workflow, I think 𝘀𝗽𝗲𝗰-𝗱𝗿𝗶𝘃𝗲𝗻 𝗱𝗲𝘃𝗲𝗹𝗼𝗽𝗺𝗲𝗻𝘁 matters more than ever.

Prompts are temporary.

Specs become team knowledge.

Curious to hear from others:
Has AI ever built exactly what you asked for — but not what you actually wanted?

If you're curious about spec-driven development, check out
```

## Pattern Rules Extracted

1. **Hook = two contrasting actions in one line.** "I stopped X. I started Y." Not a question, not a claim — a pivot.
2. **Problem = reframe in two lines.** Line 1: what people assume. Line 2: the actual issue. Short.
3. **Method = bold rule + framework questions.** State the rule in Unicode bold. Follow with 3-5 plain-text questions that define the framework. Questions grouped together (no blank lines between them).
4. **Results = stacked single-sentence outcomes.** Each result is one line. First result uses Unicode italic for contrast word. Last result can be slightly longer.
5. **Surprise pivot = "The surprising part?"** Resets reader attention before the counterintuitive insight.
6. **Counterintuitive insight = small investment → big payoff.** Bold the numbers.
7. **Punchline = contrasting pair.** Two short sentences that mirror each other structurally. "X is temporary. Y becomes Z."
8. **CTA = soft intro + single question.** "Curious to hear:" then one question. Not three questions — one good one.
9. **Link = separate from CTA.** Promo is its own section, casual tone, not salesy.
10. **Unicode bold on:** key numbers, tool names, the core method phrase, the key term in the broader context line. NOT on everything — selective emphasis.
11. **Unicode italic on:** one contrast word in the results section. Sparingly.

## Anti-Patterns (from failed drafts in this session)

- Multi-sentence paragraphs that read like essays
- Story-based hooks that need 3 sentences to set up
- Embedding questions inside paragraphs
- Using markdown bold instead of Unicode bold
- Multiple questions in CTA (one strong question > three weak ones)
- Narrative flow instead of stacked statements
- Dense paragraphs with 2-3 ideas compressed together
- Compound sentences with em dashes packing two ideas into one line
- Broader context line that tries to sneak in extra facts (keep it one clean claim)
- CTA question with "and" or em dash creating two questions disguised as one
